# 수집 플랫폼 목표 계약과 구현 순서

## 적용 범위

구현 전 설계다. 특정 사이트·공급자 선정 없이 동적 설정, 실행, 자료 보관과 소비자 연동의 공통 계약을 정한다. 아래 상태·필드명은 설계 용어이며 현재 HTTP API에 추가된 필드가 아니다. 현재 제공 동작은 [현재 업무 규칙](ddd-architecture.md#현재-업무-규칙), 정확한 HTTP 계약은 [REST Docs 원본](../src/docs/asciidoc/index.adoc)을 따른다.

구현할 때는 해당 목표 계약과 인수 조건을 함께 적용하고, 실제로 구현된 업무 규칙을 아키텍처 문서로 옮긴다. 이 문서에는 남은 설계와 그 원본 링크를 유지한다. 미구현 동작을 현재 사용 범위로 안내하지 않는다.

### 역할과 경계

- 인터넷과 다른 앱에서 자료를 수집하고, 최소 가공한 자료를 공용 DB·오브젝트 스토리지에 보관한다. 원천 앱의 업무 데이터 소유권은 원천 앱에 둔다.
- 항목 분리, 제목·본문·시각·링크 추출, 인코딩 정리와 첨부 연결을 최소 가공으로 정의한다. 원천 수정 시각을 모르면 수집 시각으로 대신 채우지 않는다.
- 요약 등 2차 가공과 블록 문서화는 Agent Docs가 담당한다. 수집으로 만들어진 문서도 직접 작성한 문서와 동등하게 취급하며 별도 검토함을 요구하지 않는다.
- Agent Docs 전달 기능은 기본 문서 시스템 안정화 이후 구현한다. push·pull·CDC는 선택하지 않고, 자료·변경 식별과 재개 계약을 먼저 정한다.
- 현재의 단일 운영자 범위를 유지한다. 웹 화면과 에이전트 도구는 같은 관리 유스케이스를 사용한다. MCP 어댑터 추가 여부는 수집 계약의 선행조건으로 두지 않는다.

### 설계 책임

출처·계획·실행·관측은 같은 수집 의미와 결정 책임을 가지므로 현재 `collection` BC에서 설계한다. 공급자나 데이터 유형만으로 BC를 나누지 않는다. Agent Docs의 문서 모델은 소비자 계약 뒤에 둔다.

- `Source`: 원천 서비스와 계정·공간의 논리적 식별, 연결 설정을 소유한다. 같은 계정의 주소·인증 참조 교체는 연결 개정으로 기록하고 출처 ID를 유지한다. 다른 계정·공간은 새 출처로 등록한다.
- `CollectionTask`: 사용할 연결 개정, 대상, 수집·추출 설정, 일정, 활성 상태와 수집 진행의 호환성을 소유한다. 공유 출처의 새 개정을 모든 계획에 조용히 적용하지 않는다.
- `CollectionRun`: 한 시도의 설정 스냅샷, 실행 소유권, 결과와 실패를 소유한다. 논리적 실행 요청과 재시도는 실행 계약으로 연결한다.
- 콘텐츠·표현·관측·진행 위치는 서로 다른 사실로 모델링한다. 이 구분만으로 새 루트나 테이블을 추가하지 않는다. 독립 삭제·보존 명령을 구현할 때는 그 일관성 단위와 루트 필요성을 [경계 선정 절차](ddd-architecture.md#새-기능을-분류하는-절차)로 판단한다.

공통 스크립트 실행기, 범용 워크플로 엔진, 메시지 버스는 이 요구의 전제로 두지 않는다. 설정으로 지원 범위를 표현하고 새로운 처리 방식은 수집기 구현으로 확장한다.

## 동적 설정과 운영 동작

### 설정 단위

1. **출처·연결:** 논리적 출처, 연결 개정, 수집기와 버전, 기본 주소, 인증 참조, 접속 정책, 원천별 요청 한도.
2. **대상·범위:** 원천의 대상 식별자, 경로·매개변수·필터, 최초 수집 범위, 이후 수집 방식. 최초 범위는 `현재부터`, `지정 범위`, `제공되는 전체` 중 수집기가 지원하는 값으로 명시한다. 오래된 자료를 제공하지 않는 원천에 과거 전체 수집을 약속하지 않는다.
3. **항목·추출:** 자료 한 건의 경계, 원천 ID와 계정·공간 범위, 필요한 필드, 첨부, 내용 비교 규칙, 추출기·출력 스키마 버전.
4. **실행·보존:** 반복 간격과 기준 시각, 실행·배치 상한, 재시도 정책, 보존 정책 참조. 설정값은 플랫폼 상한을 넘을 수 없다.

`현재부터`의 기준 시각은 해당 세대의 최초 활성화 또는 그보다 앞선 정식 즉시 실행 접수 시 확정한다. 활성 계획의 변경으로 새 세대를 만들면 그 변경을 저장한 시각에 확정한다. 샘플은 기준 시각을 만들지 않으며 중지·재개는 이를 다시 계산하지 않는다.

정기 반복 간격의 현재 지원 범위는 [현재 업무 규칙](ddd-architecture.md#현재-업무-규칙)을 유지한다. cron·달력 기반 일정은 별도 요구와 시간대·누락 시각 계약이 정해질 때 추가한다.

### 관리 흐름

- 수집기 목록과 설정 양식을 조회하고 출처·계획을 생성·조회·수정·복제한다. 새 계획은 비활성으로 생성한다. 복제는 새 계획 ID를 부여하고 진행 위치와 실행 이력을 복사하지 않는다.
- 설정 검증, 제한된 샘플 수집, 활성화, 중지·재개, 즉시 실행, 실패 재시도, 지원 범위의 과거 수집과 저장 원본 재처리를 제공한다. 지원하지 않는 동작은 접수 전에 이유를 반환한다.
- 샘플 수집은 외부 요청을 발생시키므로 일반 수집과 같은 접속·인증·요청 한도를 적용한다. 결과·추출 오류·잘린 범위를 보여주되 정식 자료, 운영 체크포인트와 정기 일정을 바꾸지 않는다.
- 샘플 확인은 선택 기능이다. 활성화에는 현재 설정의 검증 성공이 필요하며, 과거 개정에서 성공한 샘플로 현재 설정의 유효성을 대신하지 않는다. 접속 정책은 매 실행 시 다시 검사한다.
- 관리 화면은 계획 목록, 설정 편집·샘플, 실행 이력·상세, 자료·버전 조회를 제공한다. 목록에는 활성 상태, 다음 실행, 마지막 성공과 최근 실패 원인을 표시한다.
- 관리 API를 먼저 정의하고 화면·에이전트가 동일한 명령 결과와 오류를 받게 한다. HTTP 경로·필드·상태 코드는 구현 단계의 [REST Docs 테스트](development.md#api-변경)에서 확정한다.

## 수집기가 선언할 계약

수집기는 아래 정보를 버전이 있는 선언으로 제공한다. 관리 화면과 서버 검증은 같은 선언을 사용한다. 입력 형식 이름이 등록돼 있다는 이유만으로 실행 가능하다고 표시하지 않는다.

- **설정:** 수집기 ID·버전, 설정 스키마 버전, 필드 타입·필수 여부·기본값·허용 범위와 필드 간 제약. 알 수 없는 필드와 지원하지 않는 조합은 저장 전에 거절한다. URL·매개변수·추출 규칙을 무제한 실행 코드로 해석하지 않는다.
- **지원 기능:** 응답 묶음·문서·측정·파일 등 자료 단위, 스냅샷·증분·기간 지정 수집, 페이지 이동, 첨부, 삭제 증거, 저장 원본 재처리 가능 여부.
- **식별·변경:** 원천 키의 범위, 동일 자료 판정, 내용 비교 방식, 원천 수정 순서를 신뢰할 수 있는지, 출력 스키마·추출기 버전.
- **진행:** 요청에 사용하는 불투명 진행 값, 호환성을 결정하는 설정, 커서 만료 판정, 응답 범위의 완료 여부, 빈 배치와 다음 페이지의 의미.
- **연결·한도:** 지원 인증 방식, 연결 대상 제약, 요청·바이트·항목·시간 상한, 공유 요청 한도의 범위와 원천이 알려준 재시도 대기 조건.
- **오류:** 일시적 실패, 인증·권한 실패, 설정 오류, 원천 계약 위반, 커서 만료를 구별하는 코드와 비밀값 없는 설명.

플랫폼은 필수 계약이나 해당 버전 실행 코드가 없는 수집기를 활성 목록에 올리지 않는다. 수집기는 요청의 출처·계획·실행·진행 위치에 대응하는 배치와 후보 진행 위치를 반환하고, 운영 자료와 체크포인트를 직접 저장하지 않는다.

## 설정 개정과 수집 연속성

### 서로 다른 버전의 의미

- **설정 개정:** 모든 관리 변경에 증가한다. 같은 개정에 대한 동시 수정은 하나만 성공한다.
- **수집 세대:** 이전 진행 위치를 이어 쓸 수 없는 변경에만 증가한다. 이름·일정·활성 변경은 유지한다. 대상·계정 범위·원천 키·페이지 진행 의미 변경은 새 세대로 시작한다. 필터·추출 변경의 호환성은 수집기 선언으로 판단하고 선언이 없으면 호환되지 않는 것으로 처리한다.
- **추출·표현 버전:** 같은 원본을 어떤 규칙과 출력 스키마로 처리했는지 구별한다. 호환성을 보장하는 추출기 수정은 수집 세대를 유지할 수 있지만 새 표현 버전은 기록한다. 커서 형식 변경은 검증된 변환이 있을 때만 진행 위치를 이어 쓴다.

변경 검증 결과에는 진행 위치의 유지 여부, 새 세대의 최초 범위, 다음 일정 적용 시점과 대기 실행 영향을 포함한다. 호환되지 않는 변경에 최초 범위가 없으면 저장을 거절한다. 새 세대 생성은 기존 자료의 삭제 명령이 아니다. 이름만 변경하면 다음 예정 시각을 유지하고, 일정 변경·재개는 현재보다 뒤인 첫 슬롯을 계산한다.

### 실행 중 변경

- 실행을 접수할 때 출처 연결 개정, 수집기·설정·수집 세대, 요청 범위와 정책 버전을 스냅샷으로 고정한다. 비밀값은 복사하지 않는다.
- 호환되는 변경 전에 접수된 실행은 기존 스냅샷으로 진행한다. 진행 위치는 같은 세대의 실행 소유권을 취득한 뒤 읽으며, 실행 기록에 실제 시작 위치를 남긴다.
- 세대가 바뀌면 구세대의 미시작 실행과 예약 재시도를 취소한다. 이미 실행 중인 구세대 결과는 해당 세대의 이력으로 보관할 수 있지만 활성 세대의 진행 위치나 현재 자료 상태를 갱신하지 않는다.
- 저장 시 현재 실행 소유권·유효 기한, 수집 세대와 시작 시 읽은 진행 위치 개정을 함께 확인한다. 이름·일정 변경만으로 저장을 거부하지 않는다. 새 세대와의 비교·진행 위치 갱신은 같은 DB 업무 단위에서 판정한다.
- 출처 연결 개정을 바꾸는 계획은 호환성을 검증한다. 인증 값 교체는 같은 계정 범위를 유지할 때 진행 위치를 유지하며, 보안 정책의 접속 금지·권한 철회는 과거 스냅샷보다 우선한다.

## 실행과 복구

### 요청과 시도

- 정기 실행 요청은 계획과 예정 슬롯으로 식별하고 중복 생성하지 않는다. 수동 명령은 계획·명령 종류·요청 키로 중복 접수를 막는다. 같은 키·같은 내용은 같은 접수 결과를 반환하고, 같은 키·다른 내용은 충돌로 처리한다. 중복키의 보존 범위와 만료를 접수 결과에 명시한다.
- 논리적 실행 요청 하나에 여러 시도가 연결될 수 있다. 각 시도는 새 실행 ID, 시도 번호와 이전 시도 참조를 가진다. 재시도를 새 예정 시각으로 위장하지 않는다.
- 계획마다 처리 중인 논리적 요청은 하나로 제한하고, 유효한 실행 소유권도 하나만 허용한다. 실행·재시도 대기 중 겹친 정기 슬롯은 건너뛴 이유를 기록한다. 같은 계획의 새 수동 요청은 사용 중이라는 결과로 거절한다.
- 과거 수집은 별도 요청 범위와 진행 위치를 사용한다. 같은 계획의 실행 소유권을 공유하므로 정기 수집과 겹쳐 실행하지 않으며, 정상 증분 위치를 덮어쓰지 않는다.

### 중지와 완료

- 중지는 새 정기 예약을 막고 미시작 실행·예약 재시도를 취소한다. 실행 소유권을 먼저 얻은 작업은 완료할 수 있다. 중지와 시작의 판정은 DB의 조건부 변경 순서로 결정한다.
- 비활성 계획에도 명시적인 즉시 실행은 허용한다. 설정을 검증하고 같은 실행 제한을 적용하며, 활성 상태와 다음 정기 일정을 바꾸지 않는다. 중지 이후 접수한 수동 실행은 새로운 명령이다.
- 재개는 현재 설정으로 다음 슬롯을 계산하고 기존 수집 세대의 진행 위치를 이어 쓴다. 중지 기간의 정기 슬롯을 모두 재생하지 않는다. 실제 자료 공백 복구 가능 여부는 원천의 증분·과거 조회 기능에 달려 있다.
- `SUCCEEDED`는 해당 시도에 배정된 유효 배치를 오류 없이 저장하고 종료했다는 뜻이다. 여러 배치 중 하나를 저장했다는 이유로 실행을 먼저 성공 종료하지 않는다. 범위 확인 결과는 `COMPLETE`, `MORE`, `UNKNOWN`으로 별도 표시한다. `MORE`에는 다음 진행 값이 필요하고 진행 없는 반복은 실패로 처리한다. 빈 배치에 유효한 새 진행 값이 있는 경우는 정상일 수 있다.
- 범위를 이어 처리할 때는 같은 논리 요청·설정·범위 안에서 유한한 전체 기한과 처리 상한을 적용한다. 상한에 도달하면 남은 범위와 재개 위치를 표시하고 무한 후속 요청을 만들지 않는다. `UNKNOWN`이나 제한 도달을 원천 전체 조회 완료로 사용하지 않는다.

### 실패와 재시도

- 배치 단위로 확정한 자료는 이후 배치 실패에도 유지한다. 실패 결과에 저장한 건수·확인한 범위·마지막 진행 위치를 표시한다. 정상 완료와 일부 저장 후 실패를 같은 결과로 표시하지 않는다.
- 일시적 연결 장애·원천의 요청 제한은 횟수·대기·전체 시간의 유한한 상한 안에서 재시도한다. 인증·권한·설정·추출 계약 오류는 자동 반복하지 않는다. 커서 만료는 처음부터 조용히 재수집하지 않고 범위 재설정이 필요한 오류로 반환한다.
- 재시도는 같은 스냅샷과 세대의 마지막 확정 위치부터 시작한다. 세대가 바뀌거나 필요한 수집기 버전을 사용할 수 없으면 옛 요청을 재시도하지 않고 현재 설정의 새 실행이 필요하다고 알린다.
- lease가 만료된 워커의 늦은 응답은 레코드·진행 위치·성공 상태에 반영하지 않는다. 실제 외부 요청이 한 번만 발생한다고 보장하지 않는다. 실행 소유권과 유효 기한을 배치 확정 시에도 검사한다.
- lease 갱신이 없는 단계에서는 실행 기한을 lease보다 짧게 제한한다. 현재 시간·크기 기본값은 [설정 원본](../src/main/resources/application.yaml)을 유지하고, 다중 배치 실행의 전체 상한과 관계를 구현 시 검증한다.

## 자료와 관측

### 공통 자료 계약

- **자료 키:** 논리적 출처의 계정·공간 범위, 자료 유형, 원천 키로 동일 자료를 판정한다. 계획 ID, 페이지 번호와 수집 시각을 모든 자료의 정체성으로 사용하지 않는다. 원천 ID가 없으면 수집기가 유일성을 보장하는 대체 키를 선언한다. 유일한 키가 없으면 관측별 독립 자료로 지원함을 명시하고 관측 ID를 사용하거나 해당 자료 단위를 거절한다. 유일하지 않은 제목·URL·내용값으로 자료를 합치지 않는다. 식별 규칙 변경은 기존 자료와의 대응을 정의하거나 새 식별 범위를 사용한다.
- **내용 버전:** 수집기가 선언한 내용 비교 규칙으로 식별한다. 원본 바이트 해시와 최소 가공 내용의 비교값을 구별하며, 비교 규칙 버전을 보존한다. 서로 다른 출처의 유사 자료를 자동 병합하지 않는다.
- **표현 버전:** 원본 버전, 추출 규칙·추출기 버전과 출력 스키마 버전으로 식별한다. 같은 원본의 재처리를 원천 내용 변경으로 기록하지 않는다. 같은 표현 식별자에서 다른 결과가 나오면 덮어쓰지 않고 재현성 위반으로 처리한다.
- **관측:** 어느 실행·계획·세대가 언제 어떤 내용을 확인했는지 기록한다. 같은 내용은 재사용하되 마지막 확인과 관측 결과를 갱신한다. 내용이 A → B → A가 되면 콘텐츠 A는 재사용하고 마지막 A의 관측·전이는 새로 남긴다. 같은 배치의 재전달은 동일 관측이며 실제로 다시 수집한 요청은 새 관측이다.

현재 확인된 상태는 계획·수집 세대의 관측 범위와 함께 조회한다. 서로 다른 계획이나 과거 수집 결과를 무조건 하나의 전역 최신 상태로 합치지 않는다. 원천 순서를 입증할 수 없으면 수집 시각만으로 원천에서 더 최신인 버전이라고 단정하지 않는다. 과거 수집·재처리는 정상 수집의 현재 상태를 되돌리지 않는다.

### 최소 메타데이터

자료 키, 내용·표현 버전, 출처와 원천 주소, 수집 시각, 선택적인 원천 시각·원천 revision, 실행 ID·설정 개정·수집 세대, 추출기 버전, 본문 또는 객체 참조를 기록한다. 첨부에는 미디어 타입·크기·체크섬과 접근 참조를 포함한다. 하나의 원천 응답이 여러 자료의 원본이 될 수 있다.

원천 응답·파일과 최소 가공 결과를 연결해 보존 정책이 허용하는 동안 다시 처리할 수 있게 한다. 복구할 수 없는 변환은 수집기가 선언한다. 원본 수신 실패와 수신 후 추출 실패를 구별하고, 추출에 실패한 원본을 정상 자료로 공개하지 않는다. 항목 추출 실패를 조용히 건너뛰며 진행 위치를 전진시키지 않고 해당 배치를 실패시킨다.

## 저장과 공개 시점

1. 외부 요청·추출·객체 업로드는 DB 트랜잭션 밖에서 수행한다. 객체의 완전성·크기·체크섬을 확인한다.
2. 서비스의 DB 업무 단위에서 유효한 실행 소유권을 확인하고 자료·표현·관측, 공개할 변경과 후보 진행 위치를 함께 확정한다. 같은 배치의 재처리는 중복 자료·변경을 만들지 않는다. 구세대 완료는 이력만 확정한다.
3. 확정된 자료만 조회·전달 가능하게 공개한다. DB에 연결하지 못한 객체는 미참조 상태로 남기고, 재사용·정리 가능하게 식별한다. 유효한 업로드·재시도가 참조 중인 객체는 정리하지 않으며 정리가 확정된 객체는 늦은 저장에서 참조하지 못하게 한다.

DB와 오브젝트 스토리지를 하나의 원자적 트랜잭션으로 약속하지 않는다. 자료가 저장되기 전에 진행 위치를 전진시키지 않으며, 같은 배치의 DB 저장 실패는 그 배치의 관측·변경·진행 위치를 확정하지 않는다. 프레임워크 트랜잭션과 저장 책임은 [트랜잭션 계약](ddd-architecture.md#트랜잭션)을 따른다.

DB에는 식별·상태·메타데이터·작은 본문·객체 참조를 저장하고 큰 원본과 첨부는 오브젝트 스토리지에 둔다. 외부화 크기 기준은 운영 설정으로 정한다. 소비자에게 영구적인 내부 테이블명·버킷 경로를 계약으로 노출하지 않는다. 공개된 객체의 사후 유실은 가용성 오류로 알리고 복구 대상으로 기록한다.

## 삭제와 보존

- 원천 삭제, 수집 범위에서 제외, 플랫폼의 보존 만료를 구분한다. 필터 변경·목록 일부 실패·권한 상실을 자료 삭제로 해석하지 않는다.
- 원천의 명시적인 삭제 증거나, 같은 범위의 일관된 전체 목록을 확인할 수 있다는 수집기 보장이 있을 때만 원천 삭제를 기록한다. 페이지 한도·일부 실패·조회 중 목록 이동·`UNKNOWN` 상태에서는 누락 항목을 삭제로 판정하지 않는다.
- 삭제 표시는 자료 식별자·근거·시각과 함께 전달한다. 원천 삭제 후 과거 내용 유지 여부는 보존 정책으로 정한다. 삭제된 자료를 다시 관측하면 복원 사실을 새 변경으로 기록한다.
- 원본·표현·관측 이력·실행 기록·삭제 표시·소비자 변경 이력의 보존 기간을 각각 정의한다. 자동 삭제 정책이 없으면 자동 정리하지 않는다. 이는 무제한 저장 보장이 아니며 할당량에 도달하면 새 수집을 멈추고 원인을 표시한다.
- 물리 삭제 요청은 대상과 범위를 기록하고 참조 관계를 확인한다. 다른 앱이 가진 사본의 삭제까지 완료했다고 보고하지 않는다. 소비자 삭제 전파가 필요하면 대상·확인·실패 계약을 별도로 정한다.

## 소비자 계약

- 자료와 특정 내용·표현 버전, 출처·계획·세대별 목록, 본문·첨부를 안정적인 식별자로 조회할 수 있게 한다.
- 신규 자료, 내용 전이, 원천 삭제·복원, 표현 재처리, 수집 범위 변경, 플랫폼 보존 만료를 구별한다. 변경 없음 관측은 최신 확인 정보에 반영하되 내용 변경으로 전달하지 않는다.
- 현재 자료 상태 키는 자료 ID·계획 ID·수집 세대로 정의한다. 그 키 안에서 내용·표현·가용성의 공개 전이마다 상태 버전을 증가시키고, 동일 변경 재전달은 같은 상태 버전을 유지한다. 마지막 확인 시각 같은 관측 통계는 이 상태와 구분한다.
- 변경은 재전달할 수 있고 동일 변경 ID는 동일 의미를 유지한다. 소비자는 같은 변경을 다시 받아도 중복 결과를 만들지 않아야 한다. 소비자의 처리 완료 위치는 수집 체크포인트와 분리한다.
- 순서는 구독 범위 안에서 정의하고, 이어받기 경계는 조회 가능한 변경이 빠지지 않는 확정 경계여야 한다. 최대 DB ID·할당된 sequence·수집 시각만으로 미커밋 변경까지 읽었다고 판단하지 않는다.
- 최초 목록과 이후 변경을 연결할 기준 경계를 제공한다. 목록 조회 도중 발생한 변경도 기준 이후 재생해 누락 없이 동기화한다. 목록과 변경에 자료 상태 버전을 포함해 중첩 재생의 오래된 상태가 최신 결과를 덮어쓰지 않게 한다.
- 변경 보존 기간이 지난 위치는 명시적으로 만료 처리하고 전체 재동기화 방법을 제공한다. 구독 필터·세대 변경에 기존 이어받기 위치를 사용할 수 있는지도 판정한다.
- 전체 재동기화는 해당 범위에서 보존된 수집 상태 집합과 소비자의 수집 상태 사본을 대조한다. 스냅샷에 범위·기준 경계·완전성을 포함하고 완전한 대조 이후에만 해당 사본을 교체한다. 목록에 없는 항목을 원천 삭제로 단정하거나 소비자의 직접 작성·편집 문서를 삭제하지 않는다.
- 소비자 가공 실패는 수집 완료를 취소하지 않는다. 수집 성공, 전달, 소비자 처리 상태를 혼합하지 않는다.

이 계약은 pull API, push 전달과 CDC 모두에 적용한다. 구체 전송 방식과 소비자별 처리 위치 저장 주체는 연동 단계에서 정한다. CDC를 고르더라도 내부 테이블의 모든 변경을 곧바로 업무 변경으로 취급하지 않는다.

## 연결과 운영 조회

- 공개 인터넷 출처에는 현재의 공개 주소 정책을 유지한다. 내부 앱 수집에는 운영자가 지정한 호스트·포트·접속 범위 정책을 별도로 적용한다. 일반 URL 설정으로 내부망 전체를 허용하지 않는다.
- 비밀값은 참조로 등록하고 실행 시 조회한다. 계획·스냅샷·샘플·로그에는 비밀값을 넣지 않는다. 출처 인증과 이 플랫폼의 운영자 인증을 분리한다.
- 원천 서비스·계정을 공유하는 계획에 공통 요청 한도를 적용한다. 계획별 동시 실행 제한만으로 원천의 전체 quota를 지켰다고 판단하지 않는다.
- 조회에는 마지막 시도·성공·변경 발견 시각, 다음 실행, 연속 실패, 확인 범위, 신규·수정·변경 없음·거부·저장 건수와 실패 코드를 제공한다. 저장된 새 콘텐츠 수와 이번 실행이 관측한 항목 수를 구분한다.
- 운영자 화면에는 이어받기 가능 여부와 마지막 저장 지점을 표시한다. 불투명 커서는 일반 로그에 남기지 않고, 조회가 필요한 경우 운영자 접근 범위를 적용한다.

## 원천 독립 인수 조건

실제 공급자 선택 대신 아래 합성 자료와 포트 응답으로 계약을 검증한다. 이는 테스트 시나리오이며 새 네트워크 수집기를 만들라는 요구가 아니다. 테스트 작성 대상·수준은 [테스트 범위](development.md#테스트-범위)를 따른다. 아래 조건을 근거로 통합·동시성 테스트를 자동 추가하지 않는다.

### 설정과 실행

1. 지원하지 않는 인증·수집 방식이 있는 계획은 활성화·즉시 실행을 거절하고 해당 필드를 알려준다. 샘플 수집 후 운영 자료·진행 위치·일정은 그대로다.
2. 이름·일정 변경, 중지·재개 후 다음 요청은 기존 세대의 확정 위치를 사용한다. 대상 의미 변경은 새 세대와 명시된 최초 범위를 사용한다. 활성 계획을 `현재부터`인 새 세대로 바꾸면 변경 저장 시각을 기준으로 하고 이후 재개에서 바꾸지 않는다.
3. 구세대의 미시작 실행은 취소된다. 구세대 완료 결과와 만료된 소유권의 늦은 결과는 활성 세대의 자료 상태·진행 위치를 바꾸지 않는다. 만료된 결과는 이력 자료로도 저장하지 않는다.
4. 같은 수동 요청 키를 반복하면 실행 요청이 늘지 않는다. 다른 내용으로 재사용하면 충돌한다. 정기 요청의 재시도는 같은 예정 슬롯과 새 실행 ID로 조회된다.
5. 중지는 미시작 실행·예약 재시도를 취소하고 실행 중 작업은 완료할 수 있다. 과거 수집은 정상 증분 위치를 바꾸지 않는다.

### 자료 유형

1. **문서:** 같은 원천 ID의 A → A → B → A를 입력하면 콘텐츠는 A·B 두 개를 재사용하고, 관측 네 건과 A → B → A 전이를 보존한다.
2. **시계열:** 같은 종목에서 서로 다른 기준 시각의 값이 같아도 두 자료다. 같은 기준 시각의 값 정정은 해당 자료의 새 내용 버전이다. 원천이 동일 시각의 복수 측정을 허용하면 추가 차원·원천 ID로 구별한다.
3. **파일:** 같은 원천 파일 ID의 바이트 변경은 새 내용 버전이다. 같은 바이트에 대한 추출기 변경은 새 표현 버전이며 기존 원본 참조를 유지한다.
4. **목록:** 일부 페이지만 성공한 목록에서는 보이지 않은 자료를 삭제하지 않는다. 완전성과 일관성을 보장하는 수집기의 전체 목록 완료 또는 명시적인 삭제 증거에서만 삭제 표시를 만든다.

### 저장과 소비

1. 배치 하나를 확정한 뒤 다음 배치가 실패하면 앞선 자료와 위치는 남고 실패한 배치의 위치는 확정되지 않는다. 재시도는 중복 자료·변경 없이 이어진다.
2. 객체 저장 실패 시 정상 자료와 진행 위치를 공개하지 않는다. 업로드 후 DB 저장이 실패한 객체는 미참조로 추적되고, 재시도 중인 객체는 정리되지 않는다.
3. 이전 변경이 아직 미커밋인 동안 뒤의 변경이 확정돼도 이어받기 경계가 이전 변경을 건너뛰지 않는다. 최초 목록 도중 생긴 변경은 이후 재생에서 확인되고 오래된 변경이 최신 상태를 덮어쓰지 않는다.
4. 같은 변경을 재전달해도 소비 결과는 중복되지 않는다. 만료된 위치에는 재동기화가 필요하다는 결과를 반환한다. 소비자 오류가 수집 성공을 바꾸지 않는다.

상태 전이·검증은 도메인 단위, 요청·결과 조합은 출력 포트를 MockK로 대체한 서비스 단위, 저장·조회·조건부 쓰기는 각 RDB 어댑터, HTTP 계약은 전용 어댑터 테스트로 검증한다. DB 트랜잭션 자체의 동작은 프레임워크를 신뢰한다. 소비자 중복 처리 조건은 소비자 구현 시 해당 소비자의 검증 책임으로 둔다.

## 현재 구현과 변경 순서

### 1 동적 설정과 실행 가능성

현재 [관리 API](../src/main/kotlin/com/example/template/collection/adapter/inbound/web/CollectionTaskController.kt)는 재배포 없이 대상·주기·활성 상태를 변경한다. 수집기 기능 선언·설정 검증·샘플을 추가하고, 미지원 형식·인증을 실행 전에 구별한다. 기존 HTTP_JSON의 응답 묶음 단위를 명시한 채 이 관리 계약을 검증한다.

수집기 선언과 검증 결과를 같은 관리 API와 화면에서 확인하고, 샘플이 운영 자료·진행 위치·일정을 바꾸지 않는 것이 완료 조건이다. 실제 외부 공급자를 새로 선정할 필요는 없다.

### 2 진행 위치와 실행 복구

현재 [체크포인트](../src/main/kotlin/com/example/template/collection/domain/run/Checkpoint.kt)는 설정 버전과 묶여 있다. 설정 개정·수집 세대·진행 위치 개정을 분리하고, 계획별 실행 소유권, 중지·재개, 논리 요청·시도, 즉시 실행과 제한된 재시도를 적용한다.

현재 예정 슬롯의 유일 제약과 새 재시도 모델은 함께 바꿔야 한다. 기존 실행 ID·예정 시각·최종 상태와 체크포인트를 보존하는 새 마이그레이션을 사용한다. 현재 설정 버전과 일치하는 체크포인트만 초기 활성 세대에 연결하고, 불일치한 위치는 과거 범위로 보존한다. 과거 관측이나 진행 위치를 추측해 생성하지 않는다.

설정과 실행의 다섯 인수 조건, 배치 실패 후 재개 조건이 완료 조건이다. 배치 저장은 기존 실행 전체 저장보다 작은 확정 단위가 되므로 부분 저장 결과와 조회 계약을 같은 변경에 포함한다.

### 3 자료와 저장 계약

현재 [레코드 저장](../src/main/kotlin/com/example/template/collection/adapter/outbound/persistence/ExposedCollectedRecordStore.kt)은 같은 내용의 최초 관측만 남긴다. 자료·내용·표현·관측을 구별하고 현재 확인 범위·삭제 증거·보존 정책을 추가한다. 객체 저장은 참조의 완전성과 실패 복구 계약을 포함해 적용한다.

기존 레코드는 확인 가능한 최초 관측과 기존 스키마로 보존한다. 이미 사라진 반복 관측·A로의 복귀·과거 삭제는 복원했다고 표시하지 않는다. 기존 응답 묶음을 항목 단위로 바꿀 때는 새 수집기·식별·스키마 버전을 명시하고 기존 키를 조용히 재해석하지 않는다.

문서·시계열·파일·목록 인수 조건과 객체 저장 실패 조건이 완료 조건이다. 관리 조회에는 최초 관측 자료와 실행에서 확인한 자료를 구별해 노출한다.

### 4 소비자 연동

자료 조회·공개 변경·이어받기·초기 동기화 계약을 구현하고, 이후 Agent Docs 안정화 시점에 전송 방식을 선택한다. 변경 확정과 초기 목록의 경계, 재전달·만료·범위 변경 인수 조건을 확인한다.

각 단계에서 [기능 변경](development.md#기능-변경), [API 변경](development.md#api-변경), [스키마 변경](development.md#스키마-변경)에 해당하는 원본과 테스트를 함께 바꾼다. 실행·저장 유스케이스가 일관성 경계를 소유하고 외부 요청·객체 업로드와 분리하는 근거를 남긴다. 최종 검증은 [실행과 검증](development.md#실행과-검증)을 따른다.

## 적용 전에 값을 정할 항목

- 원본·표현·관측·로그·공개 변경별 보존 기간, 원천 삭제 후 사본 보존 여부, 저장 할당량. 값이 없으면 자동 삭제를 활성화하지 않는다.
- 요청·배치·논리 실행의 상한, 재시도 횟수·대기·전체 기한, 내부 앱 허용 접속 범위. 기존 기본값을 바꾸거나 자동 재시도를 활성화할 때 구체 값을 정한다.
- 필요한 인증 방식과 비밀 조회 수단. 수집기 기능 선언과 인터페이스는 먼저 정의하고 실제 연결은 제공할 수집기의 인증 방식에 맞춰 구현한다.
- 소비자 지연·변경 보존 요구와 전송 방식. Agent Docs 연동 단계에서 결정하며 수집 설정·자료 계약 설계를 막지 않는다.

실제 공급자 선정은 그 공급자의 수집기 구현과 원천 특성 검증에 필요하다. 공통 계약, 대표 유형의 자료 모델과 위 단계의 설계·검증은 독립적으로 진행한다.

## 2026-11-16 구현 범위

이 문서의 위 절은 목표 계약이다. 이번 구현은 HTTP_JSON 응답 묶음의 운영 관리와 실버 레코드 pull export에 한정한다. 응답 내부의 개별 문서 분리, 자료 상태 전이·삭제·파일·시계열 모델, 객체 저장, 자동 재시도는 구현하지 않았다.

- 수집기 기능·검증·일회 샘플·멱등 수동 실행을 제공한다. 이름·주기·중지·재개는 호환되는 체크포인트를 유지하고 출처·대상 변경은 저장된 버전 경계 이후부터 새 진행을 시작한다. 변경 전에 대기한 실행은 FAILED로 닫으며 이미 실행 중인 작업은 끝날 수 있다.
- 계획별 동시에 RUNNING 실행은 하나다. 실행 소유권 만료 결과는 기존 조건부 종료 계약으로 버린다. 같은 계획·출처·키·해시는 레코드를 재사용하며 HTTP_JSON은 전체 응답을 하나의 레코드로 유지한다. 과거 다른 계획과 공유되어 저장되지 않은 관측은 복원하지 않는다.
- 인증된 pull 방식과 공개 순번·재생은 [연동 결정](agent-docs-integration.md)에 정의했다. Agent Docs 수신기·처리 대기 목록·가공·MCP·완료 처리는 이 저장소에 구현하지 않는다.
