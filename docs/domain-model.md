# 수집 플랫폼 도메인 모델

## 경계와 구현 상태

이 시스템의 업무는 **설정한 출처에서 정해진 범위의 데이터를 반복 관측하고, 출처와 수정 이력을 설명할 수 있게 보관하는 것**이다. 주식·경제·시사·개발은 가능한 데이터 분야의 예시다. 분야 enum이나 분야별 공통 필수 열을 강제하지 않는다.

현재 동작하는 경로는 `HTTP → 관리 유스케이스 → 설정 저장소 → DB`다. 실행·레코드·체크포인트는 순수 도메인과 수집기 출력 포트로 정의했다. **수집기를 호출하는 실행 유스케이스, 일정 워커, 실제 커넥터, 실행·레코드·체크포인트 테이블은 없다.** 활성 설정을 저장해도 외부 요청은 발생하지 않는다.

| 모델 | 책임 | 현재 제공 범위 |
| --- | --- | --- |
| `Source` | 출처와 접근 형식 | 생성·조회 API, DB 저장 |
| `CollectionTask` | 수집 대상·범위·주기와 설정 버전 | 생성·조회·수정·활성 API, DB 저장 |
| `CollectionRun` | 고정된 설정으로 수행하는 한 번의 시도 | 상태 전이와 시간 규칙 |
| `CollectedRecord` | 원천 항목의 특정 내용 버전과 관측 근거 | 값 객체 검증과 배치 계약 |

설계 배경과 공식 자료는 [사례 조사](collection-research.md)에 있다. 아래 정책 중 범위·기본값은 이 초기 버전의 설계 결정이며 공급자 공통 표준이 아니다.

## 출처와 대상

`Source(id, definition, createdAt)`의 `SourceDefinition`은 이름, `kind`, `baseUrl`, 선택적 `credentialRef`를 가진다. 이름은 앞뒤 공백을 제거한 1~120자다. 출처는 생성 후 불변이며 삭제 API도 없다. 작업과 실행이 참조하는 출처의 의미가 바뀌는 문제를 초기 단계에서 피한다.

`kind`는 `HTTP_JSON`, `RSS_ATOM`, `HTML`이다. 이는 입력 형태의 분류이며 커넥터 구현 여부를 표시하지 않는다. 같은 JSON 형식이라도 SEC 공시와 GitHub 릴리스의 항목 추출·페이지 처리·식별자는 다르다. 후속 실행 구현에는 출처별 파서와 그 버전을 명시적으로 선택하는 계약이 필요하다.

`baseUrl`은 최대 2,048자의 HTTP(S) 주소다. 웹 경계에서 URI와 host를 검사하고 userinfo·query·fragment를 거부한다. 이 검사는 문법 검사다. 실행 시 DNS·연결 IP·리디렉션을 검증하는 SSRF 방어를 대신하지 않는다.

후속 커넥터의 경로 결합 계약은 baseUrl 끝의 `/`를 제거하고 resource를 덧붙이는 방식이다. 예를 들어 `https://example.org/v1`과 `/items`는 `/v1/items`를 뜻한다. parameters는 별도로 URL 인코딩한다. 현재 이 결합이나 외부 요청을 실행하는 코드는 없다.

`credentialRef`는 1~120자의 영문자·숫자·점·밑줄·하이픈으로 이루어진 비밀 저장소 참조 이름이다. 실제 비밀 값은 저장하지 않는다. 현재 참조 해결기는 없으며 공급자의 인증 요구사항도 검증하지 않는다. URL이나 일반 파라미터에 API 키를 넣으면 평문으로 저장되므로 그렇게 사용하지 않는다.

`CollectionTarget(resource, parameters)`은 다음 수집 범위를 표현한다.

- `resource`: 단일 `/`로 시작하는 경로, 최대 2,048자. 공백, query·fragment·역슬래시, `..` 경로 요소를 거부한다.
- `parameters`: 최대 50개 문자열 키·값. 키는 공백만 아닌 1~100자, 값은 최대 2,000자다. 외부 Map을 방어적으로 복사한다.

예를 들어 `/fred/series/observations`와 `series_id`, `observation_start`는 경제지표와 기간을 표현한다. `/repos/owner/repo/releases`는 특정 개발 저장소의 릴리스 범위를 표현한다. 현재는 범용 구조를 저장하며 개별 파라미터의 공급자별 의미를 검사하지 않는다. 요청 헤더·임의 코드·CSS/XPath 실행 기능은 제공하지 않는다.

## 계획, 일정, 수정 충돌

`TaskDefinition(name, sourceId, target, schedule)`은 무엇을 수집할지 정한다. 등록된 출처만 참조할 수 있고 DB 외래 키도 이를 보장한다. `CollectionTask`는 정의와 함께 식별자, `enabled`, `version`, 생성 시각을 가진다. 생성 시 `enabled=false`, `version=0`이다.

설정 교체와 활성 상태 변경은 모두 현재 `expectedVersion`을 요구한다. 저장소는 `WHERE id = ? AND version = ?` 조건으로 갱신하고, 성공 시 버전을 1 증가시킨다. 같은 버전을 가진 두 수정 중 하나만 저장된다. 최종 상태를 같은 트랜잭션 안에서 다시 읽어 DB 시각 정밀도와 응답을 맞춘다. 값이 같아도 유효한 변경 요청마다 버전이 증가한다.

트랜잭션은 서비스의 `@Transactional`이 시작하고 종료한다. 계획·출처 확인, 조건부 갱신, 결과 재조회가 같은 쓰기 트랜잭션에 참여한다. 저장소는 별도의 `transaction {}`나 트랜잭션 애너테이션을 두지 않는다. 도메인과 포트에는 Spring 의존성을 추가하지 않는다.

`IntervalSchedule(everySeconds, anchorAt)`은 **60~31,536,000초**의 고정 간격과 UTC 기준 시각을 가진다. `nextAfter(reference)`는 reference보다 엄격히 뒤인 첫 슬롯을 반환한다. 기준 시각 이전이라면 기준 시각을 반환한다. 실행이 늦어져도 기준 시각의 위상을 유지하며 지난 슬롯을 모두 재생하지 않는다.

예: 기준 `00:00`, 간격 1시간이면 `nextAfter(02:15)`는 `03:00`, `nextAfter(03:00)`는 `04:00`이다. 이 함수는 계산 규칙이며 주기 작업을 등록하거나 실행하지 않는다. cron, 지역 시간대·DST, 거래일 달력, backfill은 후속 기능이다.

DB에 저장하는 시각은 1970년부터 9999년까지다. 저장 어댑터가 마이크로초로 절삭한 뒤 DB에서 읽은 값을 반환한다. 메모리 내 일정 계산은 전달된 기준 시각의 나노초 위상을 유지한다.

## 실행의 상태와 스냅샷

`TaskSnapshot(taskId, version, definition, source)`은 실행 당시 설정을 고정한다. 작업의 sourceId와 실제 Source가 일치해야 한다. 현재 계획을 수정해도 이미 만든 스냅샷은 변하지 않는다.

실행은 `PENDING → RUNNING → SUCCEEDED 또는 FAILED`로만 이동한다. `CollectionRun.pending(...)`으로 시작하고 `start(at)`, `succeed(at)`, `fail(at, reason)`을 사용한다. 최종 상태를 다시 실행하거나 성공으로 덮어쓸 수 없다. 재시도는 새 실행 ID를 만들며 재시도 횟수·지연 정책은 아직 없다.

시각은 `scheduledFor ≤ startedAt ≤ finishedAt`을 만족한다. 수동 실행을 추가할 때 scheduledFor는 요청을 접수한 시각으로 취급할 수 있다. 실패 사유는 공백만 아닌 1~1,000자다. 오류 메시지에는 외부 비밀이나 원본 응답 전체를 넣지 않아야 한다.

현재 실행 모델은 상태 전이만 보장한다. 실행 선점, 중복 실행 방지, 프로세스 중단 복구, lease·heartbeat는 구현하지 않았다.

## 레코드와 체크포인트

`CollectedRecord(identity, schemaVersion, payload, provenance)`은 업무 필드를 강제하지 않는 공통 외피다.

- `RecordIdentity`: 1~2,048자의 원천 키와 소문자 64자리 SHA-256 `revisionHash`. 키는 논리 항목을, 해시는 특정 내용 버전을 식별한다. 현재 해시를 계산하거나 payload와 일치하는지 검증하지 않는다. 커넥터가 일관된 원문 또는 정규화 표현을 선택해 계산해야 한다.
- `schemaVersion`: 1~120자의 스키마 식별·버전 문자열. 예: `github.release.v1`. 스키마 레지스트리나 payload의 스키마 검증은 없다.
- `payload`: 비어 있지 않은 최대 1,000,000자의 문자열. 원문을 보존하므로 공백만 있는 내용도 허용한다. JSON 전용 타입이 아니며 원본 아카이브와도 구분한다.
- `RecordProvenance`: 출처 ID, 실행 ID, 수집 시각과 선택적 원천 수정 시각. 원천 시스템의 시계가 다를 수 있어 수정 시각이 수집 시각보다 미래라는 이유로 거부하지 않는다.

가격의 거래일, 경제지표의 대상 날짜·vintage, 공시의 회계 기간 등은 payload에 보존한다. 이를 공통 timestamp 하나로 대체하지 않는다. 동일 항목을 다시 관측한 이력과 내용이 바뀐 이력의 저장 방식은 실제 저장소 구현 시 구분해야 한다.

`Checkpoint(taskId, taskVersion, value)`는 특정 설정 버전에 속한 불투명 문자열이다. value는 1~16,384자이며 공급자가 해석한다. 다른 작업·설정 버전의 체크포인트로 이어 읽는 것을 거부한다. 체크포인트를 캐시 검증자나 단순 페이지 번호로 일괄 해석하지 않는다.

`CollectionConnectorPort.collect(request)`는 다음 계약만 제공하며 구현체는 없다.

1. `CollectionRequest`는 RUNNING 실행, 선택적 기존 체크포인트와 `maxRecords`를 갖는다. 한도는 기본 100개, 1~1,000개다.
2. `CollectionBatch`는 요청에 속한 레코드와 다음 체크포인트 후보를 담는다. 요청 한도와 payload 합계 4,000,000자를 넘을 수 없고, 레코드의 출처·실행이 일치해야 한다. 수집 시각은 실행 시작보다 빠를 수 없다. 목록은 방어적으로 복사한다.
3. `nextCheckpoint=null`은 기존 상태 유지다. 값이 있어도 아직 저장 완료를 뜻하지 않는다. **실제 레코드 저장이 확정된 후에만 체크포인트를 전진시켜야 한다.**

크기 제한은 메모리 내 문자 수이며 HTTP 바이트·압축 해제 크기 제한을 대체하지 않는다. 레코드 저장소·중복 제약·체크포인트 commit 유스케이스가 없으므로 현재 API로 수집 결과를 저장하거나 조회할 수 없다.

## 다음 구현의 완료 조건

첫 수집기는 허용한 실제 공급자 하나로 시작한다. 다음 항목을 함께 완료해야 “주기 수집이 동작한다”고 말할 수 있다.

1. **수집 경계:** 공급자별 대상 검증·파서·안정적인 원천 키, 페이지 이동, 파서 버전, 비밀 참조 해결, 응답 크기와 timeout을 구현한다. FRED처럼 과거 수정이 가능한 데이터에는 겹쳐 읽기나 재조회 정책을 정한다.
2. **실행과 저장:** 실행 선점·생성을 원자적으로 처리하고, 레코드·체크포인트·처리 집계를 하나의 저장 경계로 commit한다. 중간 실패 롤백, 같은 배치 재처리, 같은 슬롯의 동시 실행을 실제 DB 통합 테스트로 검증한다.
3. **실패·부하 제어:** 공유 요청 한도, 429·Retry-After, 일시 실패의 유한 재시도, 프로세스 중단 복구, 원본 보존과 민감정보 제거를 구현한다. 최소 한 번 전달과 중복 방지를 구분해 설명한다.
4. **주기 워커:** 실행 가능한 계획만 가져와 nextAfter 규칙에 맞춰 시작한다. 활성 상태뿐 아니라 실제 지원 커넥터·자격증명 준비 여부를 확인한다. 수동 실행부터 검증한 뒤 일정 실행을 연결한다.

아키텍처 검사는 계층 우선과 기능 우선 구조를 모두 지원한다. 후속 수집기·스케줄러는 대응하는 포트 역할과 같은 기능 경로의 입력·출력 어댑터 그룹에 둔다. 그룹 간 직접 의존은 금지하며 같은 그룹의 client·mapper 같은 내부 코드는 함께 사용할 수 있다. Exposed·JDBC는 출력 어댑터의 `persistence` 경로와 설정에만 둔다. 세부 규약은 [패키지 경계](code-quality.md#하위-패키지와-기능-경계)를 따른다.

수집 커넥터를 `persistence` 경로나 그룹에 두어 Exposed·JDBC 허용 범위를 넓히지 않는다. 커넥터는 별도의 출력 어댑터 첫 그룹에 둔다. 새 수집기·스케줄러를 추가할 때 정상·위반 fixture를 함께 추가한다.
